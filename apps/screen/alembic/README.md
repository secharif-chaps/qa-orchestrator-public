# Alembic Database Migrations

This directory contains Alembic database migrations for the MINT backend application.

## Migration Naming Convention

### Transition Notice (November 2025)

The project migrated from custom sequential numbering to Alembic's standard hash-based naming:

**Legacy Sequential Format** (migrations 001-003):

- `001_new_initial_migration.py`
- `002_create_user_preferences_table.py`
- `003_add_data_collection_task.py`

**Current Standard Format** (from migration d6d3b27e531e onwards):

- `d6d3b27e531e_add_task_dependencies_and_blocked_status.py`
- Uses Alembic's auto-generated revision hash
- Format: `{revision_hash}_{description}.py`

### Why the Change?

1. **Alembic Best Practice**: Hash-based naming is the standard Alembic convention
2. **Prevents Collisions**: Multiple developers can create migrations independently
3. **Automatic Generation**: No manual numbering required
4. **Migration Chain Integrity**: Alembic tracks dependencies via revision graph, not filenames

### Creating New Migrations

**Always use Alembic's auto-naming** (do not specify revision numbers manually):

```bash
# Inside Docker container
docker compose -f docker-compose.dev.yml exec backend alembic revision -m "description"

# Example output:
# Generating /app/alembic/versions/a1b2c3d4e5f6_description.py
```

The revision hash (e.g., `a1b2c3d4e5f6`) is automatically generated by Alembic.

### Applying Migrations

```bash
# Upgrade to latest
docker compose -f docker-compose.dev.yml exec backend alembic upgrade head

# Downgrade one revision
docker compose -f docker-compose.dev.yml exec backend alembic downgrade -1

# Check current revision
docker compose -f docker-compose.dev.yml exec backend alembic current

# View migration history
docker compose -f docker-compose.dev.yml exec backend alembic history
```

## Important Notes

### Running Migrations

**Always run Alembic commands inside the Docker container**, not on the host machine. The database host is configured as `db` which only resolves inside the Docker network.

### Migration Dependencies

Alembic tracks migration dependencies through the `down_revision` field in each migration file, not through filenames. The migration chain is:

```
001_new_initial_migration.py
  ↓
002_create_user_preferences_table.py
  ↓
003_add_data_collection_task.py
  ↓
d6d3b27e531e_add_task_dependencies_and_blocked_status.py
  ↓
(future migrations...)
```

### Don't Rename Existing Migrations

Existing migrations (both sequential and hash-based) should **never be renamed**. Alembic tracks applied migrations in the `alembic_version` table by revision hash, not filename. Renaming breaks the migration history.

## Migration Best Practices

1. **Descriptive Names**: Use clear, concise descriptions (e.g., `add_user_email_column`, not `update_users`)
2. **Single Purpose**: Each migration should do one logical thing
3. **Test Migrations**: Test both `upgrade()` and `downgrade()` functions
4. **Data Migrations**: For data migrations, use separate migration files from schema changes
5. **Review Before Applying**: Always review generated migration code before running

## Troubleshooting

### "Target database is not up to date"

```bash
# Check which migrations are pending
docker compose -f docker-compose.dev.yml exec backend alembic current
docker compose -f docker-compose.dev.yml exec backend alembic heads

# Apply pending migrations
docker compose -f docker-compose.dev.yml exec backend alembic upgrade head
```

### "Can't locate revision identified by"

This means a migration file was deleted or renamed. Check git history to restore the missing migration.

### "Multiple head revisions are present"

Two migrations were created in parallel. Merge them with:

```bash
docker compose -f docker-compose.dev.yml exec backend alembic merge heads -m "merge parallel migrations"
```
